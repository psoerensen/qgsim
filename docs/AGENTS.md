# AGENTS.md

## Project purpose

This repository contains `qgsim`, an R package for specifying,
validating, running, and comparing breeding-scheme simulations through a
common R interface.

The package is intended as an orchestration layer for simulation tools
implemented in R, C++, Fortran, Python, Julia, or other languages. It
should not reimplement all simulators in R. Instead, it should provide a
common specification, validation layer, backend contract, and
standardized result format.

## Repository type

## qgsim architecture rules

Preserve the explicit workflow:

``` r
breeding_scheme() -> qgsim_compile() -> qgsim_validate() -> qgsim_run() -> qgsim_result
```

Important design principles:

- Separate specification from execution.
- `qgsim_run()` should accept a compiled `qgsim_plan`.
- Avoid overlapping orchestration APIs.
- Keep `qgsim_plan` backend-neutral.
- Do not add backend-specific fields to the common plan.
- Validate individual descriptors and complete plans.
- Keep backend contracts explicit and testable.
- Standardize all backend outputs into `qgsim_result`.
- Do not wrap unconstrained backend-native output as a public result.
- Keep schema versions explicit.
- Preserve deterministic behavior for seeded reference-backend tests.

## Backend rules

Backends should follow the contract:

``` r
available()
translate()
execute()
collect()
```

Responsibilities:

- `available()` checks whether the backend can run.
- `translate()` converts a `qgsim_plan` to backend-native input.
- `execute()` runs the backend.
- `collect()` converts backend-native output into a valid
  `qgsim_result`.

Do not mix backend discovery, translation, execution, and result
collection in one function.

For external C++/Fortran/Python/Julia tools:

- Prefer file-based or JSON-based exchange formats.
- Keep backend-specific artifacts referenced through result
  files/provenance.
- Do not require external tools for core package tests.
- Add backend contract tests before adding real external integrations.

## Testing rules

Use the smallest relevant check for the change.

Common checks:

``` r
devtools::load_all()
devtools::test()
```

For focused tests:

``` r
testthat::test_file("tests/testthat/test-file-name.R")
```

For documentation changes:

``` r
devtools::document()
```

For the current minimal package, useful checks include:

``` r
Rscript -e "devtools::load_all(); testthat::test_dir('tests/testthat')"
```

Ask before running long checks or adding heavy external dependencies.

## Simulation and scientific rules

- The current `r_reference` backend is for validating architecture, not
  for scientific conclusions.
- Do not describe the reference backend as a complete breeding-scheme
  simulator.
- Do not invent simulation results, benchmarking claims, or biological
  interpretations.
- Keep examples clearly labelled as minimal or illustrative.
- Preserve reproducibility for seed-based tests.
- Add scientific realism incrementally and with tests.

## Documentation rules

- Clearly distinguish implemented features from planned backends.
- Mention that external tool integration is future/extension work unless
  implemented.
- Keep documentation concise and practical.
